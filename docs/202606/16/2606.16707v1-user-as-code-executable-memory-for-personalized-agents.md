## 摘要
个性化的人工智能智能体需要用户记忆：一种持久的用户模型，通过多次对话构建，并在每次新对话中查询。如今，这种记忆几乎总是以非结构化文本、知识图谱或扁平事实存储的形式存在，并通过检索来查询——获取与当前请求最相似的条目。这种“事实袋”记忆能够很好地回忆单个事实，但由于存储事实与执行操作是分离的步骤，它在解决矛盾、聚合多条记录或执行规则方面存在困难。我们认为，用户记忆应该是可执行的。我们提出用户即代码（UaC）这一范式，其中智能体对用户的模型是一个活的软件项目：类型化的Python对象保存用户状态，普通的Python函数编码支配状态的规则，因此对用户的表示和推理发生在解释器可运行的同一媒介中。其支撑机制是一个两阶段流水线：一个只增日志，从不丢弃任何事实，并定期检查点化为类型化代码。这改变了记忆的能力。在标准的长时对话基准测试中，UaC在召回率上达到了全上下文上界和最强先验记忆系统的水平（LOCOMO数据集上为78.8%）。其优势在表示最为关键的场景中显现。在针对用户历史的聚合问题（如“我去年进行了多少次国际旅行？”）上，基于检索的记忆表现崩溃（6-43%），而UaC保持接近完美（99%），因为答案是对类型化状态的一行计算，而非文本搜索。而且由于规则在状态变化时确定性执行，UaC能够主动触发与安全相关的告警——例如新处方药物与数月前记录的过敏症冲突——这是查询驱动记忆无法提供的能力。

## Abstract
A personalized AI agent needs a user memory: a persistent model of who the user is, built across many conversations and consulted on each new one. Today this memory is almost always stored as unstructured text, a knowledge graph, or a flat store of facts, and consulted by retrieval -- fetching the entries most similar to the current request. Such "bag-of-facts" memory recalls individual facts well, but because storing a fact and acting on it are separate steps, it struggles to resolve contradictions, aggregate over many records, or enforce rules. We argue that user memory should instead be executable. We introduce User as Code (UaC), a paradigm in which an agent's model of a user is a living software project: typed Python objects hold the user's state and ordinary Python functions encode the rules that govern it, so representing and reasoning about the user happen in one medium an interpreter can run. The enabling mechanism is a two-phase pipeline: an append-only log that never discards a fact, periodically checkpointed into typed code.   This changes what memory can do. On standard long-term conversation benchmarks, UaC matches both a full-context upper bound and the strongest prior memory systems on recall (78.8% on LOCOMO). Its advantage emerges where representation matters most. On aggregate questions over a user's history -- "how many international trips did I take last year?" -- retrieval-based memory collapses (6-43%) while UaC stays near-perfect (99%), because the answer is a one-line computation over typed state rather than a search over text. And because its rules execute deterministically whenever the state changes, UaC can surface unsolicited, safety-critical alerts -- such as a newly prescribed drug that conflicts with an allergy recorded months earlier -- a capability query-driven memory cannot provide.

## 1. 核心问题与整体含义（研究动机和背景）

- **核心问题**：当前个性化AI智能体的用户记忆大多采用“事实袋”模式（非结构化文本、知识图谱或扁平事实存储），依赖检索（如top-k相似度）来获取与当前查询最相关的条目。这种范式在回忆单个事实时表现良好，但存在三个关键缺陷：
  - **无法解决矛盾**：冲突的事实（如“我爱吃香菜” vs. “我讨厌香菜”）在无版本历史时共存，无法更新或解决。
  - **无法聚合跨记录信息**：聚合问题（如“我去年有多少次国际旅行？”）需要统计全部相关记录，但检索只能返回少数最相似条目，信息丢失严重。
  - **无法执行逻辑规则**：无法表达类似“如果护照过期日在旅行日180天内则告警”这样的确定性规则。
- **整体含义**：论文提出**用户记忆应该可执行**，即将用户模型构建为活的软件项目，使存储和推理在解释器可读写的同一媒介中完成，从而同时解决基本召回、聚合推理和主动服务三大类任务。

## 2. 提出的方法论：核心思想与关键技术细节

### 核心思想：用户即代码（User as Code, UaC）

- 将用户记忆建模为**类型化Python代码**：用户状态由Python数据类实例（`dataclass`）表示，状态间的规则由普通Python函数编码。
- 关键转变：**表示与验证的统一**——解释器可直接读取和计算状态对象，无需LLM解析文本，从而支持确定性计算和主动触发。

### 关键技术细节：两阶段流水线

1. **Phase 1：记忆（Memorize）** ——每轮对话后，LLM提取所有事实为纯文本字符串（约50-75条/会话），追加到只增事实列表中，从不覆盖或删除。相对日期被解析为绝对日期。
2. **Phase 2：结构（Structure）** ——定期（如若干会话后）LLM从完整的事实语料库重新生成整个类型化Python代码，包括：
   - 数据类定义（schema）和实例（state），如`PassportInfo`和`Trip`。
   - 持久约束（constraints）函数，如`check_drug_allergy(profile)`。
   - 计算预计算告警列表（`ACTIVE_ALERTS`）并嵌入到压缩清单（manifest）中。

### 检索与使用

- **多策略检索**：在回答用户问题时结合三个通道：
  - 结构化代码状态（`[STATE]`）
  - 事实向量检索（`[FACTS]`，ChromaDB top-20）
  - 原始对话存档检索（`[ARCHIVE]`，ChromaDB top-10）
- **生成-验证-审查循环**：用于主动服务。LLM编写约束 → 沙箱执行 → 审查结果并决定是否持久化。告警以预计算清单（约300 tokens）形式始终在智能体上下文中，无需用户提问即可触发。

### 设计原则
- 结构和数据分离（schema与instance分开）
- 统一表示与验证
- 按生活领域模块化（travel/health/finance等独立包）
- 渐进式披露（紧凑清单 + 按需加载领域）
- 智能体原生文件系统（用户项目为磁盘目录）

## 6. 主要结论与发现

1. **标准基准**：UaC在LOCOMO上达78.8%，与完全上下文上界（79.8%）无统计差异（p=0.65），显著优于同骨干SOTA复现（MemMachine 72.7%、Hindsight 69.7%、EverMemOS 55.5%等）。在LongMemEval上，UaC、完全上下文和MemMachine形成高分的顶部三簇（83-85%），彼此无显著差异。

2. **分析推理**：UaC达到99%准确率，完全上下文+Python REPL达100%，而检索系统（Mem0 6%、MemMachine 43%）崩溃。这证实了代码可执行表示在聚合计算上的结构性优势。

3. **主动服务**：UaC+约束管道在标准场景上达100%警告检出率（优于Mem0 90%），在困难场景上达85%（UaC无管道仅45%）。约束管道是关键因素。

4. **消融发现**：
   - **附加提取是最大的单一提升**（+19pp over Basic 3-tier）。
   - **两阶段分离至关重要**：增量代码会导致信息丢失（-10pp），而两阶段解决了重写问题（+12.3pp over增量代码）。
   - **类型化状态对基本召回大致中性**（-1.3pp，p=0.67），但对于分析任务和约束管道至关重要。

5. **成本与可扩展性**：尽管一次性结构化代价较高（$0.07-0.10），但结构化后每查询成本极低（~1.4 m$），在3次查询后摊销反超完全上下文的反复加载。模块化可将提示token减少14.9倍而准确率无损失。

6. **鲁棒性**：跨LLM（Gemini → GPT-5.4）结果统计上等价（p=0.82）；跨家族裁判（Gemini → Claude）排名不变，一致性好。

7. **与SOTA检索的可叠加性**：UaC + MemMachine混合在5对话子集上达到81.7%（+3.7pp），提示两者互补。

## 7. 优点：方法或实验设计上的亮点

- **创新性范式**：提出用户记忆作为可执行代码，将表示和验证统一，突破了传统检索的通病。
- **无需人工设计模式**：数据模式、约束和领域分区完全由LLM自动生成并随用户变化而演化，契合Sutton的“苦涩教训”。
- **全面覆盖记忆任务层次**：不仅覆盖基本召回，还解决聚合推理和主动告警，后者是首次有专门基准衡量。
- **严格可控的实验设计**：所有基线使用相同骨干、相同检索基础设施、相同裁判，并公开复现细节；统计检验和交叉验证使结果可信。
- **消融充分且清晰**：逐组件消融直接揭示每个模块的贡献，如附加提取+19pp、两阶段分离+12.3pp、约束管道+32.5pp主动服务。
- **主动服务基准具有现实意义**：新颖的主动安全告警场景（药物冲突、旅行证件到期）直接对应应用中的关键风险。
- **开源实现**：代码和网站公开，便于复现和产业应用。
- **成本分析全面**：超时提供了token成本、延迟、摊销分析，表明长期使用成本优势。

## 8. 不足与局限

- **写入开销**：UaC需要两次LLM调用（Phase 1 + Phase 2），而扁平事实系统只需一次。结构化成本在状态大时可能较高（如500条记录约$0.10）。
- **结构化状态对纯召回大致中性**：通道消融显示类型化Python状态在LOCOMO上贡献为-1.3pp（不显著），其价值仅限于分析推理和约束管道。因此，仅需要简单事实回忆的场景无需UaC的结构化步骤。
- **主动服务依赖管道**：没有预计算告警时UaC仅52.5%警告率，管道是关键；困难场景样本量不足（20个），对最强基线（Mem0）的差距不显著（p=0.69），需要更大样本才能确认。
- **分析推理基准合成性高**：记录是模式干净的合成数据，真实世界数据噪声更大，但这预期有利于UaC（因为解析脆弱性可能更惩罚纯文本方法）。另外，合成基准是单查询设计（最坏情况对UaC）。
- **复现忠实性和基础设施混淆**：同骨干复现可能未完全重现原系统（如省略了重新排名、更好的检索堆栈）。论文谨慎地指出原始数字是天花板而不是直接竞争对手。
- **跨LLM覆盖有限**：可移植性仅在两个最大闭源家族（Gemini和GPT）上验证，较小模型（7-8B）可能生成较低质量的代码。
- **需要沙箱执行**：存储用户状态为可执行代码需要安全的沙箱环境防止跨用户泄漏或代码注入。
- **错误约束的确定性执行**：如果LLM生成有缺陷的约束，它会每次确定性触发错误告警——正确的计算不等于正确的逻辑。
- **规模化扩展限制**：Phase 2一次全部重新生成在数百会话时遇到万亿字符容量限制，未来需要分层或增量结构化方案。
